### [Important]

**位置**

`src/sample-code-b.ts:57–91`

**問題**

`smsLogin()` 是 async 函式，但整體邏輯缺少 `try-catch` 或 `finally` 保護。若 `firstValueFrom` 拋出未預期的例外（例如 Observable 未 emit 任何值而直接 complete，會拋出 `EmptyError`），`globalLoadingService.hide()` 將永遠不會被執行，導致全域 Loading 遮罩卡住，頁面無法操作。

**為什麼**

`firstValueFrom` 的行為是：若 Observable complete 前沒有 emit 值，直接 throw `EmptyError`。這在 API 層發生錯誤轉換或 stream 提前關閉時可能觸發。Loading 狀態洩漏（stuck loading）是 UX 層的嚴重問題，且難以重現、難以偵錯。

**建議**

將 `show()` / `hide()` 改以 `try...finally` 管理，確保任何路徑下 Loading 都能被正確關閉，並集中移除散落的三次 `hide()` 呼叫：

### Before

```ts
async smsLogin() {
  // ...
  this.globalLoadingService.show();
  const [data, err] = await firstValueFrom(...);

  if (err) {
    this.globalLoadingService.hide(); // 路徑 1
    return;
  }
  if (data) {
    if (data?.err_msg_list?.length > 0) {
      // ...
      this.globalLoadingService.hide(); // 路徑 2
      return;
    }
    // ...
    this.globalLoadingService.hide(); // 路徑 3
    this.router.navigate([...]);
  }
  // data 為 falsy 且無 err 時 → hide() 從未被呼叫！
}
```

### After

```ts
async smsLogin() {
  // ...
  this.globalLoadingService.show();
  try {
    const [data, err] = await firstValueFrom(...);

    if (err) {
      // 處理錯誤（見下一個 Issue）
      return;
    }
    if (!data) return;

    if (data.err_msg_list?.length > 0) {
      this.apiErrorHandleService.openErrorDialog(data.err_msg_list);
      this.captcha?.refresh();
      return;
    }

    this.smsLoginService.setLoginData({ ... });
    this.obAuthService.setLoginFrom("sms-login");
    this.router.navigate([routeMap(PAGE_CODE.OB020)]);
  } finally {
    this.globalLoadingService.hide();
  }
}
```

### [Important]

**位置**

`src/sample-code-b.ts:72–75`

**問題**

當 API 回傳錯誤（`err` 為 truthy）時，程式碼只關閉 Loading 並 return，沒有任何使用者反饋。

**為什麼**

從使用者角度，他們點擊登入後 Loading 消失，但畫面毫無變化，不知道是網路錯誤、逾時還是其他原因。這會造成困惑，也可能讓使用者重複點擊或以為系統壞掉。對照 `data.err_msg_list` 的處理路徑，已有 `apiErrorHandleService.openErrorDialog`，但這個路徑卻沒有。

**建議**

視 `err` 的型別，至少要有一種使用者可感知的回饋。若 `[data, err]` 的 `err` 包含可識別的錯誤資訊，可直接傳入 dialog；若是通用 HTTP 錯誤，可顯示通用提示：

```ts
if (err) {
  // 依專案 error 型別選擇適合的方式
  this.apiErrorHandleService.openErrorDialog([/* 通用錯誤訊息 */]);
  return;
}
```

### [Important]

**位置**

`src/sample-code-b.ts:76–91`

**問題**

`if (data) { ... }` 區塊外沒有 else 分支。若 `data` 為 falsy 且 `err` 也沒有，程式會靜默結束，Loading 不會被 hide（在未採用 `finally` 的當前版本下尤其明顯）。

**為什麼**

`[data, err]` 的 tuple 模式應保證二擇一，但若底層 API 封裝實作有誤，或 Observable 回傳了 `[null, null]` 的邊界情況，現有代碼無法應對。

**建議**

搭配上方 `finally` 的修改後，可將 `if (data)` 改為 early return 的守衛型寫法，讓主流程更清晰：

```ts
if (!data) return; // 防禦性守衛
// 以下直接處理 data
```

### [Suggestion]

**位置**

`src/sample-code-b.ts:78`

**問題**

`if (data)` 區塊內部仍使用了 `data?.` 可選鏈（`data?.err_msg_list`、`data?.candidate_name`、`data?.otp_proc_token`）。

**為什麼**

在已通過 `if (data)` 守衛後，TypeScript narrowing 已排除 null/undefined，再使用 `?.` 會讓閱讀者誤以為 data 此時仍可能為空，造成語義混淆。

**建議**

`if (data)` 區塊內直接使用 `data.xxx`，或搭配上方的 early return 改寫，讓型別窄化更直觀。
